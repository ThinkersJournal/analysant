  03-ir.md:17  [Intermediate representation > The DAG] **The graph is the model, independent of any input.** It is built when a model is loaded or imported — **not** when a forward pass runs — and is ideally fully optimized before the first input arrives. Inputs and per-session state flow *through* the persistent graph (via storage; see below); the graph itself is not rebuilt per input, per token, or per session. "No graph until `forward()` runs" is a defect this architecture corrects.
  03-ir.md:18  [Intermediate representation > The DAG] **Immutable nodes after creation.** A node's op, inputs, dtype, and shape are fixed at construction — where "shape" is the node's *static shape expression*: a concrete dim vector, or (for data-dependent ops) a **capacity/upper-bound shape** whose true valid extent is carried at runtime by a separate count, never by mutating the node (see [Data-dependent output shapes](#data-dependent-output-shapes)). An optimizer that wants to change a node inserts a new node and rewrites consumers' edges to the new id. This makes graph rewrites tractable and lock-free reading possible.
  03-ir.md:19  [Intermediate representation > The DAG] **Append-only arena, with compaction.** Optimization is append-only — rewrites add nodes and rewire consumers; superseded nodes are left orphaned. Because `optimize_graph`'s pathfinders explore many candidate paths the optimizers then discard, the arena accumulates substantial orphaned debris, so **compaction is required, not optional**: a compaction pass drops unreachable nodes, keeping only the base map plus the surviving optimized multi-path graph. It runs at least **before finalize-to-disk** (so the persisted `.fuel` holds the lean result, not exploration debris) and optionally **between optimization rounds** (to bound the in-memory / disk-backed working set during a long search). This is not a *correctness* concern — orphans never change results — but under the heavy-exploration optimizer it is very much a *size* concern, on disk especially (RAM less so: orphaned pages of an mmap'd graph simply never fault in).
  03-ir.md:20  [Intermediate representation > The DAG] **Side-table metadata.** Information derivable from the graph (view-op layouts) or varying independently of node identity (tolerance budgets, storage, per-path kernel assignments, profile data) lives in side tables keyed by NodeId (and, for session state, by `(NodeId, SessionId)`), not on the node. The node is the structural fact; side tables are interpretations and instances.

  03-ir.md:73  [Intermediate representation > Higher-order primitives: `Op::Scan`] **Encoding.** The recurrence body is carried as the node's own `inputs`, exactly like `Op::Branch`'s arms: `inputs = [init_carry, xs_0..xs_{n_xs-1}, consts.., body_new_carry, body_y]`. The two body-*exit* NodeIds are always the **last two** inputs — the convention that lets `base_map_hash`'s existing input-recursion hash the body for free, with only a params-only `op_key` arm added for `Op::Scan` itself (over `n_xs`, `bound`, `emit`, and whether `early_exit.is_some()` — never the predicate's identity). Nodes inside the body reference `Op::ScanPlaceholder { role, index }` leaves instead of real operands: `role: Carry` for the per-step carry-in (always `index: 0` — v1 is single-carry), `role: Elem, index: i` for the per-step slice of `xs[i]`. Consts are referenced by ordinary `NodeId` (they don't vary per step). `Op::ScanPlaceholder` is an inert, input-less leaf substituted only by `unroll_scan`; it is never itself realized.
  03-ir.md:74  [Intermediate representation > Higher-order primitives: `Op::Scan`] **Single carry tensor, v1.** Exactly one carry threads through the recurrence in Phase 1 — no carry tuples. Multi-carry is a possible future extension, not built.

  03-ir.md:143  [Intermediate representation > The optimized form: the multi-path graph (the plan IS the graph)] **Alternatives are paths, not a per-node side-table.** A region with two viable implementations (a CPU path and a CUDA path; a fused vs unfused form) appears as two sub-paths that branch from a common node and reconverge at a later common node. The points where paths diverge are **decision points** (branch points); everything between two decision points is a fixed **run** that dispatches as a unit. Decision points are **few** — most of the graph is a single agreed run — which is what lets the runtime decide rarely and dispatch long sequences rather than choosing per op (see [06-runtime](06-runtime.md)).
  03-ir.md:147  [Intermediate representation > The optimized form: the multi-path graph (the plan IS the graph)] **The surviving paths are a bounded Pareto frontier, per ending device.** `optimize_graph` does not keep every alternative — that explodes combinatorially (the 2026-06-14 decisions-log entry records the prototype that demonstrated this). It keeps, per ending device, the Pareto-optimal paths over the ranked axes — **one central time metric, per-tier memory, precision, accuracy** — which stays naturally small (order 10²) because those axes are kept low-dimensional (a single time metric, memory as tiers, discrete precision/accuracy). A **crowding-distance cap (keep-per-device)** is the hard backstop. The cap is **per ending device** (up to `keep` each, crowding-reduced) — never a single N across all devices, which would strand slow devices (the scalar-top-N failure mode). So ≥1 path per device survives automatically, and the total is ≤ `keep` × devices: on a 5-device machine with a fast-but-memory-heavy and a slow-but-light kernel per device, ~2 Pareto-optimal paths per device (~10 total) is the intended outcome — not "3 total." Multiple paths survive per device deliberately: a fast-but-memory-heavy path and a slow-but-light one are both kept (the runtime picks by current memory pressure), and a path may span devices (so two paths colocated at one node are *not* mergeable). Convergence merges two paths only when they are **forward-identical** from a point on; never strand the last path for a (device, backend).

  06-runtime.md:15  [Runtime > The runtime's responsibilities] **Path resolution at decision points.** At the few decision points (branch points) of the multi-path graph, the runtime selector picks among the surviving per-device Pareto paths by current telemetry (device load, per-tier free memory). Between decision points the path is fixed.
  06-runtime.md:16  [Runtime > The runtime's responsibilities] **Run dispatch.** Dispatching the fixed **run** between two decision points as a unit (a pre-recorded command sequence where the backend supports it), not op-by-op — assigning runs to available backend slots as their inputs become ready.
  06-runtime.md:17  [Runtime > The runtime's responsibilities] **Data-parallel execution.** Dispatching independent runs concurrently when slot capacity and memory permit.
  06-runtime.md:18  [Runtime > The runtime's responsibilities] **Synchronization at join points.** Waiting on outputs from multiple parallel branches before a join op.
  06-runtime.md:22  [Runtime > The runtime's responsibilities] **Strategic decisions** (placement, fusion, kernel-variant choice) — the optimizer's. The runtime executes the path the picker chooses.
  06-runtime.md:23  [Runtime > The runtime's responsibilities] **Kernel implementation** — the backend's. The runtime calls `KernelRef` function pointers; what they do is opaque.
  06-runtime.md:24  [Runtime > The runtime's responsibilities] **Cache management** — [11-persistence](11-persistence.md)'s. The runtime loads the persisted graph and writes refined plans, but doesn't decide cache policy.
  06-runtime.md:67  [Runtime > Dispatch: runs, not single ops] **Shallow (just-in-time)**: commit the next run only as a slot frees. Maximum adaptivity; risk of backend idle while the picker thinks. For very small runs where decision overhead dominates.
  06-runtime.md:68  [Runtime > Dispatch: runs, not single ops] **Deep**: queue many runs ahead. Backends always busy; risk that telemetry has shifted by execute-time. For very large runs where execution dominates.
  06-runtime.md:69  [Runtime > Dispatch: runs, not single ops] **Bounded (default)**: keep exactly enough runs queued to fill currently-available slots; queue more only as one finishes. Balances adaptivity vs throughput — backends never idle, decisions stay current. The bound = sum of backends' currently-available slot counts.
  06-runtime.md:79  [Runtime > Data parallelism: independent runs run concurrently] The ready-set tracks all runs whose inputs are available and frontier-finalized.
  06-runtime.md:80  [Runtime > Data parallelism: independent runs run concurrently] Each ready run is dispatched to an available slot on its assigned backend.
  06-runtime.md:81  [Runtime > Data parallelism: independent runs run concurrently] Across backends, multiple runs are simultaneously in flight; within one backend, multiple slots dispatch to the device's parallelism primitives (CUDA streams, Vulkan queues, CPU sub-pools).

  06-runtime.md:177  [Runtime > What this rules out] **No silent runtime fallback to a different op.** A chosen kernel failing (OOM, hardware fault) surfaces the error; the runtime doesn't transparently switch paths without telling the user. JIT-registered kernels are cost-gated by the route picker and surface through telemetry; a kernel that doesn't win is never used.
